# Issue #3 — расследование мобильного подключения (локально)

## A. Root Cause Analysis

**Для первоначального отказа на 1.1.1 установлена программная причина:** при «авто DC» Android передавал пустой `dc_ips` и исключал прямой WebSocket DC2/DC4. Оставались пользовательский Worker (если задан), общий CF и прямой TCP fallback; в исходном отчёте доступный альтернативный маршрут не наблюдался. Это видно в [issue #3](https://github.com/Derigava/tg-ws-proxy-android/issues/3), [diff PR #4](https://github.com/Derigava/tg-ws-proxy-android/pull/4/files) и [коммите Android-адаптера](https://github.com/Derigava/tg-ws-proxy-android/commit/98ff7cd8d697edd1c34f7a9ee635ec68b432885b). Текущий [ProxyController.kt#L11-L13](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/java/com/amurcanov/tgwsproxy/ProxyController.kt#L11-L13) задаёт 2 и 4; [#L41-L76](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/java/com/amurcanov/tgwsproxy/ProxyController.kt#L41-L76) передаёт их сервису; [android_proxy.py#L177-L197](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/python/android_proxy.py#L177-L197) парсит список, [#L310-L327](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/python/android_proxy.py#L310-L327) применяет его к ядру. Таким образом, **PR #4 устранил конкретную ошибку конфигурации**. При ручном режиме пустые адреса остаются возможным сознательным выбором.

**Причина продолжающегося отказа «Wi‑Fi да, LTE нет» после релиза 1.1.2 не установлена.** [Сообщение после релиза](https://github.com/Derigava/tg-ws-proxy-android/issues/3#issuecomment-6946688663) и [отчёт Tele2](https://github.com/Derigava/tg-ws-proxy-android/issues/3#issuecomment-6957274164) не содержат контролируемой сравнительной трассы одной версии/настроек и не указывают точный номер установленного APK. CF `TimeoutError()` не локализует стадию DNS/TCP/TLS/WS. Локальный listener может успешно работать при полной недоступности внешних маршрутов: [upstream `_handle_client`](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/tg_ws_proxy.py#L315-L333).

Путь: Telegram → локальный listener Android [`ProxyService.kt#L81-L139`](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/java/com/amurcanov/tgwsproxy/ProxyService.kt#L81-L139) → JSON [`ProxyEngine.kt#L9-L59`](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/java/com/amurcanov/tgwsproxy/ProxyEngine.kt#L9-L59) → [`android_proxy.py#L310-L400`](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/python/android_proxy.py#L310-L400) → [`tg_ws_proxy.py#L265-L351`](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/tg_ws_proxy.py#L265-L351) → WS pool [`pool.py#L32-L75`](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/pool.py#L32-L75), или Worker → CF → TCP fallback [`bridge.py#L138-L183`](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/bridge.py#L138-L183) → Telegram DC. Прямой WS использует [DC IP, SNI/Host и `/apiws`](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/pool.py#L173-L192), [TLS и HTTP Upgrade](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/raw_websocket.py#L92-L165). Пул пополняется асинхронно, так что «WS pool unavailable» на холодном старте само по себе не подтверждает блокировку WS.

## B. Матрица гипотез

Уверенность означает уверенность **в указанном статусе**, а не вероятность самой гипотезы. Все offline-симуляции проверяют поведение программы, а не сеть оператора.

| Гипотеза | Поддержка / противоречие | Код; воспроизведение и минимальный тест | Возможное изменение; статус / уверенность |
|---|---|---|---|
| H1 Фильтрация оператора | После 1.1.2 есть Wi‑Fi/LTE расхождение у [пользователя](https://github.com/Derigava/tg-ws-proxy-android/issues/3#issuecomment-6946688663), но нет пакетов/трассы; разные операторы и [отказы вне Android](https://github.com/Flowseal/tg-ws-proxy/issues/1583) не доказывают единой блокировки. | [RawWebSocket.connect](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/raw_websocket.py#L92-L165); на **одном телефоне** с теми же настройками сравнить DNS/TCP/TLS/WS на Wi‑Fi и LTE с `scripts/diagnose_routes.py`. | Исправлять только после определения фильтруемой стадии; **не доказана, средняя**. |
| H2 Смена сети | Адаптер уже обрабатывает default network, потерю VALIDATED и [сбрасывает TCP/CF backoff и idle pools](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/python/android_proxy.py#L343-L369); [callback](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/java/com/amurcanov/tgwsproxy/ProxyService.kt#L180-L225). | H4 Регрессия Android | Старый авто-DC действительно был ошибкой [PR #4](https://github.com/Derigava/tg-ws-proxy-android/pull/4/files), но текущий main передаёт DC2/DC4 даже при CF; [тесты конфигурации и backoff](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/tests/python/test_android_proxy.py#L175-L228) проходят. Общность **симптома** подтверждена; общность **программного дефекта** — нет.

## D. Proposed Fix — сравнение стратегий

| Стратегия | Сложность / совместимость | Вероятность помочь конкретному отказу / риск |
|---|---|---|
| A. Android-адаптер | Исходный дефект исправлен PR #4; дополнительная лёгкая **внешняя диагностика без изменения приложения** совместима. | Определит стадию отказа, не восстановит сама маршрут; минимальный риск. |
| B. Обновить/исправить Flowseal | Высокая: проверить vendoring, lock/hashes, API Chaquopy, Android crypto, тесты и APK. | Пока нет воспроизводимого общего дефекта; риск регрессии высок. |
| C. Поменять выбор маршрутов/backoff | Средняя-высокая; затрагивает Worker, прямые DC, расход энергии/число соединений. | Может помочь после доказательства задержанного восстановления, сейчас спекулятивно. |

**Первоначальный выбор до полевых логов:** не добавлять сетевой патч. Причина после 1.1.2 тогда не была локализована; дополнение ниже отражает более поздние измерения и обратимое изменение.

## E. Implementation / проверки

Локальная ветка `fix/mobile-network-connectivity` создана от `main` (`21c8a1c`), `main` не менялась. Изменены только локальные **новые** файлы:

- `scripts/diagnose_routes.py`: разовый DNS→TCP→TLS (с проверкой CA и SNI)→HTTP Upgrade, `--family 4|6`, разделение прямого DC IP и SNI, безопасный Worker dst/DC, максимум 8 разрешённых адресов, 1 попытка на каждый; вывод JSON содержит только стадию/тип ошибки/HTTP статус, без доменов и секретов. Не отправляет MTProto. **HTTP 101 не валидирует `Sec-WebSocket-Accept` и не проверяет передачу Telegram-трафика.** Синхронный системный DNS не имеет отдельного timeout.
- `tests/scripts/test_diagnose_routes.py`: 9 offline-тестов DNS, TCP, TLS, WS, успешный ответ, IPv4, IPv6, fallback адресов и Worker path; fake sockets.
- `tests/python/test_mobile_route_matrix.py`: 6 offline-тестов порядка Worker→CF→TCP, CF off, восстановления, наличия DC2 в WS pool при CF on; моки маршрутов ядра, **не** реальная сеть.
- Этот отчёт.

На исходном `main`: **263 passed**; после изменений: **278 passed** командой `python scripts/run_python_tests.py` (в изолированном Python 3.13 venv, включая vendored upstream, адаптер и scripts). `python -m compileall` и `git diff --check` выполнены без ошибок. `scripts/diagnose_routes.py --help` запущен; локальный пробный TCP-check выполнился и сообщил `tcp/TimeoutError`, не полевой мобильный тест. Первоначальная проверка до установки JDK/SDK не собирала APK; последующие результаты полевой сборки и исправления указаны ниже. Измерений батареи на устройстве нет.

### Полевой тест (только на затронутом Android-устройстве)

1. Подтвердить в настройках Android и журнале приложения **точную** версию 1.1.2 и `Target DC IPs: DC2, DC4`, включённый CF, список собственных Worker и время событий. Работать на одном устройстве, в одной точке, с одними настройками. Не публиковать `tg://proxy`, secret, полный журнал или приватное имя Worker; перед передачей вручную проверить редактирование.
2. Передать скрипт в Termux с Python 3. Переключить Wi‑Fi → LTE → Wi‑Fi; на каждом этапе (без VPN/Private DNS или с одинаковыми настройками) запустить **по одному разу**:

   В CF-команде заменить `<CF-base-domain>` **реальным** доменом из настроек/безопасного журнала, не буквально этой строкой. 3. Во время активного соединения сделать Wi‑Fi→LTE и LTE→Wi‑Fi, затем при неизменной сети восстановить ранее недоступный маршрут. Записать секунды до восстановления, число открытий соединений за минуту, закрытия старых сессий, `WS pool`, `CF proxy failed`, `TCP fallback` и состояние Android `VALIDATED`. ## F. Remaining Risks

Реальная фильтрация Tele2/Билайн/Ростелеком не воспроизведена. Некоторые CF-маршруты могут возвращать HTTP 101, но ломаться на MTProto; инструмент этого не видит. Прямой IPv4 может зависеть от NAT64. Активные сокеты и H2 pool остаются при `network_changed()` ([android_proxy.py#L362-L369](https://github.com/Derigava/tg-ws-proxy-android/blob/21c8a1c/app/src/main/python/android_proxy.py#L362-L369)); пока неизвестно, создаёт ли это зависание. CF breaker до 300 секунд и TCP backoff до 3600 секунд могут задерживать восстановление на той же сети; сброс при смене сети есть, но полевой замер отсутствует. Нельзя считать mock-тест подтверждением подключения у Tele2. Прямой `WS pool unavailable` может быть обычным холодным стартом. Тесты не проверяют работу собственного Worker на мобильном операторе и корректность APK.

## G. Decision

**NEEDS FIELD TEST.** Исходный Android-дефект устранён PR #4, но причина сохраняющихся после релиза мобильных отказов недостаточно установлена для нового сетевого патча. После контролируемых замеров пересмотреть H1/H2/H3/H6; не закрывать issue #3 и не публиковать PR/release до подтверждения.

## Дополнение: полевые логи 1.1.2-diag и проверка существующего WS:80

Пользователь уточнил: на его Samsung SM-S928B приложение не работает **ни на Wi‑Fi, ни на LTE**. В журнале `tgwsproxy-log (1).txt` (локальный пользовательский артефакт, не публиковать целиком) две независимые пробы 16:11:29 и 16:12:40 показывают одинаково: TCP к прямому IPv4 DC2 `149.154.167.220:443` завершается таймаутом; CF DNS разрешается, TCP по IPv4 открывается, но TLS handshake зависает; по IPv6 TCP возвращает `OSError` без точного кода. В 16:12:32 зарегистрирован сброс маршрутов после восстановления сети; в 16:13:19 статистика `ws=0 cf=0 tcp_fb=0 up=0.0B down=0.0B`. Это подтверждает недоступность **проверенных** маршрутов на устройстве, но не конкретную причину сетевой фильтрации и не доступность остальных 19 CF-доменов. Статистика `tcp_fb=0` означает отсутствие **успешного** TCP fallback, а не доказательство отсутствия попыток.

Локальная контрольная проверка того же включённого Flowseal-ядра на другом компьютере дала `HTTP 101` как для прямого `149.154.167.220:443`, так и для первого домена CF через WSS:443 и WS:80; это проверка инфраструктуры **с другой сети**, не результат на телефоне. [Flowseal #1491](https://github.com/Flowseal/tg-ws-proxy/issues/1491) описывает случай, где CF Worker по WSS зависал на ClientHello, а WS:80 возвращал 101; автор upstream предложил настройку «Выключить TLS для CF-прокси и CF-worker». Ядро уже реализует `ProxyConfig.disable_secure` и передаёт `secure=not proxy_config.disable_secure` для CF/Worker ([bridge.py, строки 215–217 и 248–252](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/bridge.py#L215-L252)); [RawWebSocket.connect](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/raw_websocket.py#L92-L112) выбирает TCP:80 без TLS. Прямой WS-пул по-прежнему использует TLS, а H2 выключается [config.py#L79-L82](https://github.com/Flowseal/tg-ws-proxy/blob/2085861957070eeea07990a522b29f42e5230210/proxy/config.py#L79-L82).
