## Что не удалось подтвердить кодом

1. **«Приложение не собирает данные»** — утверждение верно настолько, насколько можно судить по зависимостям и манифесту: SDK аналитики нет, сетевые вызовы идут только к GitHub (проверка обновлений), Cloudflare/Worker и DC Telegram. Полного доказательства отсутствия сбора код не даёт; формулировка в README намеренно узкая — «нет аккаунтов, аналитики и телеметрии».
2. **«Свой воркер не делит квоту с другими пользователями»** — унаследованное утверждение из README/CHANGELOG Flowseal и `values-ru/strings.xml:151`. В коде видно только порядок попыток (`bridge.py:144–157`), но не механика квот Cloudflare; проверить это можно лишь на живом Worker.
3. **Полный паритет с ByeByeDPI 1.8.2** — не заявлен и не должен заявляться: `docs/byebyedpi/parity.md:47–51` и `:229–231` прямо фиксируют, что наблюдение на устройстве не выполнялось, а часть пунктов (T-04, T-05, видеопоток, always-on) не реализована. README говорит «модуль на основе», а не «полная замена».
4. **Скриншоты `docs/assets/screens/01-two-modules.png` … `08-dpi-settings.png`** — файлы появились в ветке одновременно с этим текстом; галерея ссылается на них по именам. Если композиции будут пересняты, подписи нужно сверить заново: они описывают конкретные состояния (выбранный YouTube, включённый CDN, вкладка TG-WS в журнале).
5. **Social preview и Topics** — проверяются только в Settings репозитория; API отдаёт текущие значения (`homepage`, `topics`), но загруженное превью через API не читается. Инструкция в `metadata.md` описывает действие владельца, а не проверенный результат.
6. **«Оба модуля работают одновременно»** — подтверждено скриншотом `docs/assets/screenshots/raw/04-both-active.png` и композицией `docs/assets/screens/04-both-live.png`, а также логикой исключения себя из VPN (`DpiVpnRouting.kt:33–36`), но не автотестом на физическом устройстве: `docs/byebyedpi/release-checklist.md` помечает сценарий «Независимость движков» как **не проверено**.
